1. Übersicht

Die Python Bridge startet aus Godot heraus einen oder mehrere Python-Subprozesse (je Instanz ein eigener Prozess) und kommuniziert mit ihnen über WebSocket auf 127.0.0.1. Sie übernimmt automatisch:

  • venv-Verwaltung: legt pro Projekt ein virtuelles Environment unter python_bridge/venv/ an (einmalig).
  • Dependency-Management: installiert websockets + frei konfigurierbare Pakete (z. B. numpy) per pip.
  • Python-Erkennung: findet eine installierte Python (3.8+) selbst, ohne fest verdrahteten Pfad.
  • Task Manager: zentrale Warteschlange mit Prioritäten, Timeout, Cancel, Retry und Backpressure.
  • Frame-Synchronisation: Python-Antworten werden gepuffert und kontrolliert im Haupt-Thread verarbeitet – kein Frame-Stall.
  • Task-Batching: kurz aufeinanderfolgende Aufrufe werden optional zu einem Paket zusammengefasst.
  • Health Monitoring & Crash-Restart: Ping/Pong-Überwachung, automatischer Neustart mit Exponential Backoff.
  • Typisierten Transport: JSON für Skalare, Binär-Chunks für große Daten (NumPy-Arrays, Bytes, Bilder).
  • Persistente Skript-Kontexte: Skripte und deren Zustand (Importe, Variablen, Funktionen) bleiben in der Instanz erhalten.
  • Hot Reload: geänderter Python-Code wird erkannt und per Konfiguration neu geladen.
  • Editor-Integration: Python-Editor-Dock mit Syntax-Highlighting und deterministischer GDScript-Wrapper-Generierung.

2. Architektur

              Godot (GDScript)                                   WebSocket                           Python-Prozess
        PythonBridge (Autoload/Facade)
          ├─ TaskManager  (Queue, Priorität, Batch, Retry)
          ├─ Scheduler    (Frame-Sync, Inbox, Budgets)
          └─ BridgeInstance (je Instanz)
               ├─ BridgeProcessManager
               ├─ BridgeConnectionManager          ⇄  ws://127.0.0.1:<port>          ⇄  run_server.py
               ├─ BridgeHealthMonitor                 Text = JSON · Binary =          ├─ server (asyncio + Worker-Thread)
               └─ BridgeProvisioner (venv, pip)       Header + Chunks                ├─ executor (Kontexte, Source-Hash)
                                                                                      ├─ introspection (AST)
                                                                                      └─ serializer · protocol (v2)

Der Ablauf: Godot startet den Python-Server als Subprozess. Der Server schreibt Port + PID in python_bridge/tmp/<instanz>.json. Godot liest die Datei, verbindet sich per WebSocket, sendet ein hello und gilt nach der hello_ack-Antwort als READY.

Invariante: Python wartet nie auf einen Godot-Frame, und Godot wartet nie auf Python. Eingehende Ergebnisse werden im Scheduler gepuffert und innerhalb eines definierten Sync-Punkts (max. max_results_per_frame pro Frame) verarbeitet. Jede Anfrage trägt eine eindeutige id; Antworten werden darüber den Tasks zugeordnet.

Nachrichten-Typen (Protokoll v2): hello → hello_ack · task / batch → task_result / task_error / batch_result · cancel → cancel_ack · ping → pong · reload → reload_ack · introspect → introspect_result · shutdown → shutdown_ack · event · status

3. Installation in einem neuen Projekt

  1. Den Ordner addons/python_bridge in das Zielprojekt nach addons/ kopieren.
  2. Godot öffnen → Projekt → Projekteinstellungen → Plugins → „Python Bridge“ aktivieren. Das Plugin registriert den Autoload-Singleton PythonBridge automatisch.
  3. Python 3.8+ muss installiert sein (die Bridge findet sie über PATH, PYTHON_PATH oder python_executable).
  4. Beim ersten Start wird automatisch python_bridge/venv/ erzeugt und websockets (+ konfigurierte Pakete) installiert – das kann 1–3 Minuten dauern.
Hinweis: Das venv liegt im Projektordner. Damit Godot es nicht als Ressourcen importiert, enthält python_bridge/venv/ eine .gdignore-Datei. Das Plugin kopiert die Python-Quellen bei jedem Start nach python_bridge/bridge/, damit Quell- und Laufzeit-Version immer identisch sind.

4.3 PythonBridgeTask

Ein Task durchläuft die Zustände QUEUED → RUNNING → COMPLETED | FAILED | CANCELLED | TIMEOUT. Ergebnis und Fehler sind über das Signal done(result: PythonBridgeResult) abrufbar (genau einmal pro Task).

FeldBeschreibung
id · instance_idEindeutige Task-ID; instance_id = "" bedeutet Auto-Zuordnung an eine beliebige bereite Instanz.
priorityGanzzahl, 0 = höchste Priorität (stabile Reihenfolge bei gleicher Priorität).
commandrun | call | define
context_id · source · function · args · kwargs · inputAusführungsdaten des Tasks.
timeout_msMaximale Gesamtlebensdauer (Queue + Ausführung); Überschreitung → TIMEOUT.
max_retries · retries_left · retry_policyRetry-Konfiguration (Policy: none | connection_error | process_error | all).
batchableErlaubt dem Scheduler, den Task in ein Batch-Frame zu fassen (Standard true).
result · meta · stateEndergebnis, Metadaten (z. B. duration_ms) und aktueller Zustand.

Konstruktoren (statisch): PythonBridgeTask.make_call(id, context, source, function, args, kwargs, timeout_ms, priority := 0), make_run(...), make_define(...).

5.2 Verhalten

  • Priorität: 0 = höchste; stabile Reihenfolge (FIFO) bei gleicher Priorität.
  • Timeout: ein Timer pro Task (Queue + Ausführung); bei Überschreitung wird ein CANCEL best-effort gesendet und der Task auf TIMEOUT gesetzt.
  • Cancel: Queue-Tasks werden sofort entfernt; laufende Tasks werden markiert und als CANCELLED abgeschlossen (späte Ergebnisse werden verworfen).
  • Retry: nur gemäß retry_policy; retries_left wird dekrementiert, der Task mit retry_delay_ms neu eingereiht.
  • Backpressure: max_queued_tasks und max_payload_bytes lehnen Tasks mit strukturiertem Fehler ab (Queue voll / Payload zu groß).
  • Frame-Sync: Ergebnisse landen in einer begrenzten Inbox; pro Frame werden max. max_results_per_frame verarbeitet. Ein wachsender Backlog throttle den Dispatch – stabile Framezeiten statt maximaler Antwortgeschwindigkeit.
  • Batching: kompatible, batchbare Tasks derselben Priorität an dieselbe Instanz werden bis max_batch_size oder max_batch_delay_ms gesammelt. Ein einzelner Task wartet nie auf weitere; eine höhere Priorität bricht das Fenster ab. Reihenfolge und Semantik bleiben erhalten; ein Fehler innerhalb eines Batches betrifft nur den betroffenen Item (separate Ergebnisse).
  • Crash-Behandlung: bei Verbindungsabbruch oder Prozess-Ende werden In-Flight-Tasks gemäß Policy gefailt oder erneut eingereiht; die Instanz startet mit Exponential Backoff neu (Counter-Reset nach stable_uptime_ms).

6. Datentransport & Typen

Skalare bleiben lesbares JSON. Strukturierte Werte werden als getaggte Objekte {"$pb": "<tag>", ...} kodiert. Große Binär-Blobs (> 512 Bytes) wandern nicht als Base64 in den JSON-Header, sondern als Binär-Chunks im Frame (U32LE(Header-Länge) + HeaderJSON + [U32LE(Chunk-Länge) + Chunk]*). 7. Python-Seite

7.1 Skript-Konventionen

  • execute / execute_script: Das Skript erhält die Eingabe in der Variablen input und legt das Ergebnis in result ab.
  • call_script: Die benannte Funktion wird mit args / kwargs aufgerufen; ihr Rückgabewert geht an Godot.
  • Persistente Kontexte: Jede context_id hat einen eigenen Namespace. Der Executor speichert einen Source-Hash; call_script re-definiert den Kontext nur, wenn sich der Quelltext geändert hat.
  • Fehler: Python-Exceptions werden strukturiert gemeldet ({code, type, message, traceback}) – der Server-Prozess bleibt am Leben.
  • stdout/stderr: werden pro Task erfasst und im Ergebnis mitgeliefert.

7.2 Aufbau des Python-Pakets

DateiZweck
run_server.pyEntry-Point: CLI-Parameter (--bind --port --tmpdir --tag), startet den asyncio-Server.
python_bridge/server.pyWebSocket-Server: routet task / batch / cancel / reload / introspect / ping / hello / shutdown; Nutzer-Code läuft in genau einem Worker-Thread pro Instanz, damit der Event-Loop reaktionsfähig bleibt; Watchdog beendet den Prozess nach Shutdown/Verbindungsabbruch.
python_bridge/executor.pyVerwaltet Kontexte, führt define / run / call aus (Source-Hash), fängt Exceptions, capturet stdout/stderr, unterstützt Cancellation.

8. Editor-Integration

Das Plugin registriert den Autoload PythonBridge und hängt ein leichtgewichtiges Dock-Panel (rechts oben) an. Der Editor spricht ausschließlich mit der Facade – keinerlei Runtime-Logik im Editor.

ElementBeschreibung
Dock-Panel (editor/python_editor.gd)Skriptliste (auto-refresh), CodeEdit mit Python-Syntax-Highlighting, Aktionen: Save · Run · Generate wrapper · Hot reload · Refresh · New script, Status + Log, mtime-Watcher für externe Änderungen.
Syntax-Highlighting (editor/python_syntax_highlighter.gd)Keywords, Builtins, Strings, Kommentare, Zahlen, Dekoratoren.
Wrapper-Generator (editor/wrapper_generator.gd)Deterministisch (gleiches Schema → identische Bytes); Marker-Header; überschreibt nur markierte Dateien; class_name-Kollisions-Check; Python-Defaults bleiben autoritativ (Sentinel-Check).

Wrapper-Beispiel: Aus def calculate(a: int, b: int) -> int: return a + b erzeugt der Generator ein GDScript wie bridge.calculate(2, 3). Der originale .py-Code bleibt unverändert und außerhalb von Godot lauffähig. Wrapper werden nur erzeugt, wenn man sie anfordert (Button bzw. auto_generate_wrappers).

10. Lebenszyklus, Provisioning & Fehlerbehandlung

9.1 Lebenszyklus & Provisioning

  1. PROVISIONING – Workspace-Ordner anlegen (scripts/, tmp/, config/), Python erkennen (≥ 3.8), Bridge-Python nach python_bridge/bridge/ kopieren.
  2. venv – falls nicht vorhanden: python -m venv …/venv (nicht-blockierend, Timeout 120 s).
  3. pip – pip install websockets>=11 + konfigurierte Dependencies (Timeout 300 s, Log in tmp/pip.log), anschließend Import-Verifikation.
  4. STARTING – run_server.py als Subprozess starten; Server schreibt tmp/<instanz>.json (Port + PID).
  5. CONNECTING → HANDSHAKE – WebSocket-Verbindung aufbauen, hello senden.
  6. READY – hello_ack empfangen; Tasks sind jetzt möglich.

Crash & Restart: Ein unerwarteter WebSocket-Close oder ein toter Subprozess im READY-Zustand löst die Restart-Policy aus: max_restart_attempts Versuche mit Exponential Backoff (500 ms → 1000 ms → 2000 ms, konfigurierbar), Counter-Reset nach stable_uptime_ms. Es bleiben keine Zombie-Prozesse zurück (vor jedem Neustart wird ein eventuell noch laufender Prozess beendet).

Graceful Shutdown: Beim Beenden von Godot (shutdown()/_exit_tree) werden neue Tasks blockiert, shutdown an alle Instanzen gesendet, auf shutdown_ack (bzw. Timeout shutdown_timeout_ms) gewartet und Prozesse notfalls zwangsweise beendet.

9.2 Fehler-Taxonomie

Jeder Fehler trägt einen Code aus der Taxonomie (PythonBridgeErrorHandler). Der Status eines PythonBridgeResult wird daraus abgeleitet.

CodeBedeutungStatus
PYTHON_EXCEPTION · TASK_ERRORPython-Exception bzw. Task-Fehlererror
TIMEOUT_ERRORAntwort kam nicht rechtzeitigtimeout
PROCESS_ERROR · CONNECTION_ERRORProzess-/Verbindungsfehlerdown
DEPENDENCY_ERROR · SERIALIZATION_ERROR · PROTOCOL_ERROR · BRIDGE_ERRORInfrastrukturfehlerinternal

Eine Python-Exception enthält mindestens: Exception-Typ, Message, Traceback, Task-ID, Instanz-ID – nie nur „Something went wrong“.
