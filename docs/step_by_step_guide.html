Python Bridge – Schritt-für-Schritt-Anleitung

Version: 0.3.0  |  Plattformen: Windows, Linux, Web (Pyodide)  |  Godot: 4.x (entwickelt und getestet gegen 4.7)

Diese Anleitung zeigt den kompletten Weg: Plugin installieren → Python-Dateien im mitgelieferten Python-Editor-Dock schreiben → GDScript-Code verbinden → Export auf Linux, Windows und Web testen.

Das Wichtigste in einem Satz

Python-Dateien leben im Projekt unter python_bridge/scripts/. Die Bridge startet automatisch einen Python-Prozess (Desktop) bzw. eine Pyodide-Runtime (Web) und stellt dieselbe GDScript-API für beide Wege bereit. Dein Spielcode und dein Python-Code unterscheiden nicht zwischen den Plattformen.

1. Installation und Einrichtung

Schritt 1.1 – Plugin installieren

  1. ZIP (PythonBridge-Plugin-0.3.0.zip) entpacken.
  2. Den Ordner addons/python_bridge/ komplett in dein Godot-Projekt kopieren, sodass res://addons/python_bridge/ entsteht.
  3. Godot (neu) starten bzw. das Projekt öffnen.

Schritt 1.2 – Plugin aktivieren

  1. Projekt → Projekteinstellungen → Plugins.
  2. Haken bei Python Bridge setzen.

Das Plugin macht automatisch zwei Dinge:

  • Registriert den Autoload-Singleton PythonBridge (alle API-Aufrufe laufen über dieses Objekt).
  • Öffnet das Dock „Python Bridge“ (rechts oben) – dein Python-Datei-Editor mit Syntax-Highlighting.

Schritt 1.3 – Python prüfen (nur Desktop relevant)

Die Bridge braucht ein lokales Python 3.8+ (empfohlen: 3.10–3.12). Sie erkennt python3 / python (Linux) bzw. python.exe / py (Windows) automatisch.

python3 --version      # Linux
python --version       # Windows

Keine manuelle venv nötig: Beim ersten start_instance() erzeugt die Bridge automatisch den Workspace (python_bridge/scripts|modules|plugins|packages|tmp) und eine virtuelle Umgebung mit allen Abhängigkeiten. Der Log im Dock zeigt den Fortschritt ([PROV]-Zeilen); die erste Einrichtung dauert daher kurz.

Schritt 1.4 – Projekt frühzeitig prüfen (Export-Check)

# im Projektordner ausführen:
python3 addons/python_bridge/tools/export_check.py --project . --platform linux
python3 addons/python_bridge/tools/export_check.py --project . --platform windows
python3 addons/python_bridge/tools/export_check.py --project . --platform web

Der Check meldet fehlende Konfiguration bevor du exportierst (Runtime, Versionen, Schreibrechte, Web-Bundle, Presets). Mit --json für CI, --fix für sichere automatische Korrekturen.

2. Python-Dateien im Python-Editor schreiben

Schritt 2.1 – Erstes Skript anlegen

  1. Dock „Python Bridge“ öffnen.
  2. New script klicken, als ID math_tools eingeben.
  3. Es wird python_bridge/scripts/math_tools.py angelegt und als Tab geöffnet.

Schritt 2.2 – Funktionen schreiben

Beispielinhalt (zwei Funktionen für die späteren Aufrufe):

def calculate(a, b):
    """Addiert zwei Zahlen."""
    return a + b


def summarize(values):
    """Summiert eine Liste von Zahlen."""
    return sum(values)

Der Editor bietet: mehrere Tabs, Dirty-Marker (* vor dem Namen), Zeilennummern, Python-Syntax-Highlighting, externen-Änderungen-Watcher (lädt nicht-dirty Tabs automatisch neu) und Hot-Reload-Button.

Schritt 2.3 – Speichern und testen

  1. Save klicken – schreibt die Datei (Registry-Cache wird automatisch verworfen).
  2. Run klicken – führt das Skript über execute_script() aus. Beim ersten Mal startet die Python-Instanz default automatisch (venv-Erstellung, siehe Log).
  3. Ergebnisse und Fehler (inkl. Python-Traceback) erscheinen im Logbereich des Docks.

Tipp: Ein Skript, das mit Run getestet werden kann, darf eine Variable result setzen: result = calculate(2, 3). Das Ergebnis erscheint im Log.

Schritt 2.4 – Wrapper generieren (optional, empfohlen)

  1. Skript-Tab aktiv lassen, Generate wrapper klicken.
  2. Es entsteht python_bridge/wrappers/MathToolsWrapper.gd mit einer typisierten GDScript-Methode pro Python-Funktion (Signaturen kommen aus der AST-Introspection).

Generierte Dateien tragen einen Marker und werden nur als generierte Dateien überschrieben – eigene Wrappers bleiben sicher.

3. GDScript: die Bridge im Spiel verwenden

Schritt 3.1 – Minimalbeispiel

Neues Skript an einen Node hängen (z. B. Main.gd):

extends Node

func _ready() -> void:
    # Instanz starten (Desktop: Python-Prozess, Web: Pyodide) – identischer Code!
    var start = await PythonBridge.start_instance()
    if start.is_error():
        push_error("Bridge-Start fehlgeschlagen: " + start.error_message())
        return

    # Skript-Funktion aufrufen
    var r = await PythonBridge.call_script("math_tools", "calculate", [2, 3])
    if r.is_ok():
        print("2 + 3 = ", r.value)
    else:
        print("Fehler (%s): %s" % [r.error_code(), r.error_message()])
        if r.error.has("traceback"):
            print(r.error["traceback"])

Schritt 3.2 – API-Überblick

AufrufZweck
await start_instance(name)Instanz starten (provisioniert venv/Workspace automatisch)
await execute(code, input)Einmaliger Code, Ergebnis über Variable result
await execute_script(id, input)Gesamtes Skript ausführen
await call_script(id, func, args, kwargs)Einzelne Funktion aufrufen (persistenter Kontext)
await define_script(id)Skript dauerhaft in den Kontext definieren
create_script(id, code)Python-Datei schreiben (nutzt auch das Dock)
hot_reload_script(id)Kontext invalidieren und neu laden
introspect_script(id)Funktions-Signaturen abfragen (Basis für Wrapper)
submit_task / cancel_task / task_doneTask-API: Prioritäten, Batching, Timeout, Cancel
materialize_data / release_dataGroße Ergebnisse (DataRef-Handles) nachladen/freigeben

Schritt 3.3 – Generierten Wrapper nutzen

# statt call_script(...) direkt typisiert:
var math := PyBridgeMathTools.new()
var r := await math.calculate(2, 3)

Schritt 3.4 – Hot Reload im Alltag

  1. Python-Datei ändern (im Dock oder extern), Save.
  2. Hot reload klicken (oder automatisch: der Watcher erkennt Disk-Änderungen nicht-dirty Tabs).
  3. Der nächste Aufruf nutzt den neuen Code; Godot-State bleibt unangetastet.

4. Parameter und Rückgabewerte

GDScriptPythonHinweis
int, float, bool, Stringint, float, bool, str1:1
Array, Dictionarylist, dictJSON-kompatibel, beliebig verschachtelt

Fehler sind immer strukturiert: r.error enthält code (Kategorie, z. B. PYTHON_EXCEPTION), type (Python-Exception-Typ), message und traceback.

4.5 Cython-Module (Desktop, optional)

Schritt 4.5.1 – Toggle aktivieren

Im Python-Editor-Dock die Checkbox „Als Cython-Modul kompilieren (.pyx)“ aktivieren. Die Datei wird ab sofort als .pyx gespeichert (eine bestehende .py wird umbenannt, der Inhalt bleibt).

Schritt 4.5.2 – Cython-Typen nutzen

import numpy as np            # Importe immer auf Modulebene

__bridge_deps__ = ["numpy"]

def smear(list xs, int passes):
    cdef double s = 0.0
    cdef int i
    for i in range(passes):
        s += xs[i % len(xs)]
    return s * 0.5

Schritt 4.5.3 – Aufrufen wie ein normales Skript

var r := await PythonBridge.call_script("mathtools", "smear", [3.5, 100_000])

Der Build passiert automatisch vor dem ersten Aufruf (oder per Button „Compile Cython“). Nur veränderte Module werden neu kompiliert.

  • Compiler: System-Compiler, wenn vorhanden — sonst installiert sich die Bridge den Compiler selbst in die venv (pip-Paket ziglang). Kein Compiler-Setup auf dem Zielrechner nötig.
  • Web: Cython ist im Browser nicht möglich (kein C-Compiler in Pyodide) — der Export-Check warnt bei .pyx-Dateien.
  • Erster Build dauert einige Sekunden — Hot-Reload-Zyklen lieber in .py entwickeln, produktiv dann auf .pyx umschalten.

5. Export-Test Linux

Schritt 5.1 – Preset anlegen

Projekt → Export → Hinzufügen → Linux.

Schritt 5.2 – Prüfen

python3 addons/python_bridge/tools/export_check.py --project . --platform linux

Erwartet: 0 Fehler. Geprüft werden Python-Version (≥3.8), Schreibrechte für venv, Bridge-Dateien und Preset.

Schritt 5.3 – Exportieren und laufen lassen

  1. Exportieren.
  2. Das Spiel braucht auf dem Zielsystem ein installiertes Python 3 (die Bridge provisioniert venv + Abhängigkeiten beim ersten Start selbstständig im Nutzer-/Spielverzeichnis).
  3. Erster Start: die [PROV]-Logzeilen zeigen die Einrichtung; danach verhält sich das Spiel wie im Editor.

6. Export-Test Windows

Schritt 6.1 – Preset anlegen

Projekt → Export → Hinzufügen → Windows.

Schritt 6.2 – Prüfen

python3 addons/python_bridge/tools/export_check.py --project . --platform windows

Der Check auf dem Build-Rechner verifiziert Projekt-Layout und Preset. Die Runtime-Regeln gelten auf dem Windows-Zielsystem: Python 3 installiert (Microsoft Store oder python.org), Bridge findet python.exe/py automatisch; Workspace + venv werden beim ersten Start angelegt.

Schritt 6.3 – Exportieren und testen

Exportieren, .exe starten; im Zweifel zuerst python --version in der CMD des Zielsystems prüfen. Der Log im Spiel (bzw. Konsole) zeigt die Provisionierung.

7. Export-Test Web (wichtig)

Konzept: Im Browser gibt es keine lokalen Prozesse, keine venv, keine TCP-Sockets. Die Bridge nutzt deshalb auf Web automatisch einen zweiten Transport: Pyodide (Python als WebAssembly) läuft in einem Web Worker mit virtuellem Dateisystem. Deine GDScript-Aufrufe und dein Python-Code bleiben identisch – die Bridge wählt den Transport selbst. NumPy, SciPy und Pandas sind verbindlich unterstützt und funktional getestet (echte Berechnungen: linalg, FFT, Matmul, Integration, GroupBy/Merge).

Schritt 7.1 – Web-Preset anlegen

Projekt → Export → Hinzufügen → Web.

Schritt 7.2 – Web-Bundle bauen

# im Projektordner:
python3 addons/python_bridge/tools/build_web_bundle.py \
    --project . --out build/web_bridge --packages numpy,scipy,pandas

Ergebnis in build/web_bridge/:

bridge_worker.js        der Pyodide-Worker (aus dem Addon)
bridge_workspace.tar    dein Python-Code + Bridge-Runtime (virtuelles FS)
bridge-lock.json        aufgelöste Versionen (Reproduzierbarkeit)
pyodide/                optional: lokale Runtime (offline-fähig)

Statisches Hosting: Alles sind statische Dateien – GitHub Pages genügt. Ohne lokalen pyodide/-Ordner lädt der Worker die Runtime vom jsDelivr-CDN (Fallback). Mit --local-pyodide <entpacktes-pyodide> läuft alles CDN-frei von deinem Host.

Schritt 7.3 – Exportieren und zusammenlegen

  1. Web-Preset exportieren (Zielordner, z. B. build/web/).
  2. Den Inhalt von build/web_bridge/ neben die Export-Dateien kopieren (index.html, *.wasm usw.).

Erwartetes Layout:

export-ordner/
├── index.html
├── godot.web.wasm  (+ .js/.pck)
├── bridge_worker.js
├── bridge_workspace.tar
├── bridge-lock.json
└── pyodide/            (optional)

Prüfen:

python3 addons/python_bridge/tools/export_check.py --project . --platform web

Schritt 7.4 – Lokal testen

cd export-ordner
python3 -m http.server 8000
# Browser: http://localhost:8000

Die Browser-Konsole zeigt: Pyodide-Load, Workspace-Entpacken, Pakete (numpy/scipy/pandas), bridge host ready, danach deine [demo]/print-Ausgaben. Falls Threads-Fehler auftreten, exportiere ohne „Thread Support“ oder setze die Header COOP/COEP (GitHub Pages unterstützt Custom-Header nicht – dann die Single-Thread-Variante nutzen; die Bridge funktioniert in beiden Fällen).
